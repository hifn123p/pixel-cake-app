## 1. 现状盘点：差在哪

`EditParams` 当前的全部可调项：

| 分组 | 参数 | 范围 |
|---|---|---|
| 影调 | 曝光 `exposureEv` | −2..2 EV |
| | 对比度 `contrast` | −1..1 |
| | 阴影 `shadows` | −1..1 |
| | 高光 `highlights` | −1..1 |
| 色彩 | 色温 `temperature` | −1..1 |
| | 色调 `tint` | −1..1 |
| | 饱和度 `saturation` | −1..1 |
| 曲线 | `lumaPoints` | 3 锚点（黑场/中间调/白场） |
| LUT | `lutId` / `lutIntensity` | 5 个内置 |

**共 10 个可调项**（7 个滑块 + 1 条曲线 + 2 个 LUT 参数）。对照 Lightroom：

| LR 分区 | 项数 | PixelCake |
|---|---|---|
| Light（WB 2 + Tone 6 + Presence 5） | 13 | 4 缺 9 |
| Color Mixer（8 色相 × H/S/L） | 24 | **0** |

| Curves（RGB + 分通道） | 4 条 | 1 条（仅亮度） |

缺口集中在三块：**① 影调分区不全**（只有阴影/高光，没有黑场/白场/自然饱和度）；
**② 颜色完全没打开**（没有 HSL 混色、没有色调分离）；**③ 局部/效果/细节全空**。

## 2. 目标参数全表

命名一律用**英文驼峰**（与现有 `exposureEv` / `lumaPoints` 一致），UI 文案用中文。
「成本类」见 §4：**P** = 逐像素可进 `PixelProgram`；**C** = 需像素坐标；**N** = 需邻域。

### 2.1 影调（Tone）— 批次 1，最高性价比

| 参数 | 范围 | 默认 | 语义 | 成本 |
|---|---|---|---|---|
| `blacks` | −1..1 | 0 | 黑场：只动暗部末端，**加法**抬/压真黑 | P |
| `shadows` | −1..1 | 0 | 阴影（已有，语义改为「正=提亮」） | P |
| `highlights` | −1..1 | 0 | 高光（已有，**语义翻转为「正=提亮」**，见 §6.3） | P |
| `whites` | −1..1 | 0 | 白场：只动亮部末端 | P |
| `highlightRecovery` | 0..1 | 0 | 线性域软压肩，救回被曝光推爆的高光 | P（但在**线性域**） |

四区权重（`L` = sRGB 亮度 0..1）：

```
wBlack(L)     = clamp((0.25 − L)/0.25)²
wShadow(L)    = exp(−(L−0.22)² / (2·0.20²))
wHighlight(L) = exp(−(L−0.78)² / (2·0.20²))
wWhite(L)     = clamp((L − 0.75)/0.25)²

dL = 0.35·blacks·wBlack + 0.35·shadows·wShadow
   + 0.35·highlights·wHighlight + 0.35·whites·wWhite
r += dL; g += dL; b += dL        // 加法：必须能抬真黑（乘法抬不动 0）
```

> **为什么用加法而不是乘法**：`0 × k ≡ 0`。LR 的 Blacks 能把纯黑抬起来，只有加法做得到。
> 代价是加法会轻微压缩对比，所以系数取 0.35 而不是 1，并在后面用对比度/曲线补回。

### 2.2 偏好（Presence）— 批次 1

| 参数 | 范围 | 默认 | 语义 | 成本 |
|---|---|---|---|---|
| `vibrance` | −1..1 | 0 | 自然饱和度：**按当前饱和度反比加权**，护肤色 | P |
| `dehaze` | −1..1 | 0 | 去朦胧（**近似版**：抬黑点 + 轻度对比 + 微增饱和） | P |

```
// vibrance：已经很艳的地方几乎不动，灰的地方多给
sat = (max−min)/max
f   = 1 + vibrance · (1 − sat)
c   = L + (c − L)·f

// dehaze 近似：正=去雾（压黑点），负=加雾（抬黑点）
b0 = −dehaze · 0.10            // 注意符号，正 dehaze → b0 < 0
c  = (c − b0) / (1 − b0)
```

> **「清晰度 / 纹理」不在本表**：它们是**中/高频局部对比**，必须有模糊参考图 ⇒ 邻域算子，
> 属批次 4。把 `clarity / texture` 塞进逐像素路径只会得到「对比度」的复制品
> ——**名字骗人比没有更糟**。

### 2.3 颜色（Color）

#### 2.3.1 HSL 混色（批次 2）

8 个色相通道，每通道 3 项 = **24 项**：

| 参数 | 形态 | 范围 |
|---|---|---|
| `hsl.hue` | 8 项 | −1..1（跨通道旋转色相） |
| `hsl.sat` | 8 项 | −1..1 |
| `hsl.lum` | 8 项 | −1..1 |

通道中心角（度）与 LR 一致，宽度不等（红/橙更窄）：

```
Red 0 | Orange 30 | Yellow 60 | Green 120 | Aqua 180 | Blue 240 | Purple 275 | Magenta 315
```

混合规则：像素色相落在某通道时，**同时**平滑渗入相邻通道（`w = 1 − d/halfWidth`，取最近两个），
不做硬切 —— 硬切会在色相过渡带上留下可见的台阶（渐变天空最先暴露）。

```
(dH, dS, dL) = Σ wᵢ · (hueᵢ, satᵢ, lumᵢ)
h' = h + dH · 30°                     // 单通道满量程 ≈ ±30°，与 LR 手感接近
c' = (c − L)·(1 + dS·1.0) + L
c'' = c' + dL·0.25
```

> **`≥ 30° 的色相旋转必须给上限**：超过约 ±40° 后「橙→黄绿」的映射会让肤色直接变绿，
> 用户会认为 App 坏了。UI 上把满量程定在 ±30°，而不是让它一路转到 ±180°。

#### 2.3.2 彩色分级 / 色调分离（批次 2）

4 个分区 × (色相/饱和/明度) = 12 项，外加 `blending` / `balance` 2 项 = **14 项**。

```kotlin
data class GradingBand(val hue: Float = 0f, val sat: Float = 0f, val lum: Float = 0f)

data class ColorGrading(
    val shadows: GradingBand = GradingBand(),
    val midtones: GradingBand = GradingBand(),
    val highlights: GradingBand = GradingBand(),
    val global: GradingBand = GradingBand(),
    val blending: Float = 0.5f,   // 分区过渡锐度
    val balance: Float = 0f       // 分区界线整体平移
)
```

数学：`hue` → RGB 单位色向量 `tint`；分区权重复用 §2.1 的四区权重（`blending` 控 σ、`balance` 控中心）。

```
gain = Σ wᵢ(blending, balance) · satᵢ
c += tintᵢ · gain · 0.20            // 着色（加法，保持中性灰不动）
c += lumᵢ · wᵢ · 0.25               // 分区明度偏移
```

> 这是**美图秀秀「色调分离」的同类功能**，也是「电影感」的主要来源（阴影压青、高光偏橙）。
> 成本极低（两条通道的乘加），性价比仅次于影调四区。

#### 2.3.3 分通道曲线（批次 2）

`EditParams` 加 3 条曲线，形态与现有 `lumaPoints` 完全相同（复用 `ToneCurve` 三锚点 + `buildLumaLut`）：

| 参数 | 说明 |
|---|---|
| `redPoints` / `greenPoints` / `bluePoints` | 每通道 256 项 LUT |

UI：曲线分类加一行 chip（`亮度 / 红 / 绿 / 蓝`），复用现有 3 滑块布局 —— **零新控件**。

### 2.4 效果（Effects）— 批次 3，**需坐标**

| 参数 | 范围 | 默认 | 说明 |
|---|---|---|---|
| `vignetteAmount` | −1..1 | 0 | 正=提四角，负=压四角 |
| `vignetteMidpoint` | 0..1 | 0.5 | 作用起点半径（映射后**四角恒定吃满权重**） |
| `vignetteFeather` | 0..1 | 0.5 | 过渡宽度 |
| `vignetteRoundness` | −1..1 | 0 | 正=像素正圆，负=轮廓贴住画幅 |
| `grainAmount` | 0..1 | 0 | 强度 |
| `grainSize` | 0..1 | 0.35 | 颗粒尺寸（**按长边归一化**：长边上铺 1200 → 300 个颗粒，对数插值） |
| `grainRoughness` | 0..1 | 0.5 | 颗粒对比（对噪声做**带符号幂整形**，0.5 恰好是恒等） |

> ⚠️ **三条必须守住的坐标纪律**（都与现有项目规则一致）：
> ① `PixelProgram.applyLinear(r,g,b)` **原本收不到坐标** ⇒ 批次 3 **改了签名**：三条入口
> （`applyLinear` / `applySrgb8`）各多收一对**长边归一化坐标** `(u, v)`，且**刻意不给默认值**
> （给默认值会让「某个调用点忘了传坐标」退化成「暗角/颗粒静默失效」，编译不过比跑错好）；
> ② 暗角与颗粒的几何量一律用**长边归一化坐标**（`u = (x + 0.5f) / max(w, h)`）—— 本项目预览 2048、
> 导出 7008，用像素坐标会导致「预览与导出不是同一个效果」。颗粒尤其致命：`grainSize` 必须按长边
> 缩放，否则同一张照片在预览与导出里颗粒粗细差 3.4 倍。
> ③ 颗粒噪声**不用 `Random`、也不用逐像素哈希**，而是预烘一张 **512×512 的确定性噪声瓦片**
> （`(x, y)` 整数哈希 + 两次 3×3 环绕盒式模糊 + 方差归一化）：逐像素只做「一次乘 + 一次取整 +
> 一次查表」，且同一位置永远同一个值 —— 否则拖动任意滑块时噪点每帧重掷，画面会「沸腾」。
> 尺寸不烘进瓦片，而是体现在**采样密度**上（`grainSize` → 长边上的格数），一张瓦片覆盖整段量程。

### 2.5 细节（Detail）— 批次 4，**需邻域**，✅ 已落地

| 参数 | 范围 | 说明 |
|---|---|---|
| `sharpenAmount` | 0..1 | 锐化强度 |
| `sharpenRadius` | 0.5..3 | 半径**倍率**（`长边/1000 × 本值`，**不是像素数**） |
| `sharpenDetail` | 0..1 | 高频/低频分配 |
| `sharpenMasking` | 0..1 | 边缘蒙版（0=全图，1=只锐边缘） |
| `nrLuminance` | 0..1 | 亮度降噪 |
| `nrLuminanceDetail` | 0..1 | 亮度细节保留（1 = 该级完全不改像素） |
| `nrColor` | 0..1 | 色度降噪 |
| `nrColorDetail` | 0..1 | 色度细节保留 |
| `clarity` / `texture` | −1..1 | 中/高频局部对比（清晰度 / 纹理） |

**这一批不是「再加几个滑块」，而是加一条渲染通路** —— 原估的「必须在分带渲染之外做（模糊核跨带）」
**是对的**，但对代价的估计偏悲观：**不需要**动 `EditEngine` 的分带架构，也不需要按
`banded-image-operator-refactor` 给分带算子补「源行上下界外扩」。

实际方案是**在已物化的目标位图上再跑一遍独立的分带 pass**（`DetailPass`）：它自己管窗口与 halo，
`PixelProgram` 的签名与既有调用点**零改动** ⇒ 回归面反而**小于**批次 3。
代价是它**不是** `(u, v)` 的纯函数 ⇒ 只能说「预览与导出**观感一致**」，不能说逐位相同（§12 第 2 条）。

细节见 §12（落地记录）与 `DetailPass` 的类 KDoc（含三条「为什么作用在 sRGB8 平面上」的理由）。

## 3. 管线顺序重构

现有顺序（`ColorMath` 文档 + `PixelProgram.finish`）：

```
白平衡(线性) → 曝光(线性) → sRGB编码 → 阴影/高光 → 对比度 → 饱和度 → 亮度曲线 → 内置LUT
```

目标顺序（**粗体 = 新增**）：

```
【线性域】
  1  白平衡            温度 / 色调
  2  曝光              exposureEv
  3  **高光找回**      highlightRecovery   ← 软压肩，替代硬截断（见 §5）
  4  线性 → sRGB 编码   查表

【sRGB 域 · 逐像素】
  5  **影调四区**      黑场 / 阴影 / 高光 / 白场
  6  对比度            contrast
  7  亮度曲线          lumaPoints
  8  **自然饱和度**    vibrance
  9  饱和度            saturation
 10  **HSL 混色**      8 通道 × H/S/L
 11  **彩色分级**      阴影 / 中间调 / 高光 / 全局
 12  **分通道曲线**    red / green / blue
 13  内置 LUT          lutId / lutIntensity
 14  **暗角**          需坐标
 15  **颗粒**          需坐标 + 确定性噪声

【邻域 pass · 独立通路（批次 4）】
 16  清晰度 / 纹理 / 锐化 / 降噪
```

把这个顺序当成**规格的一部分**写进代码 KDoc：顺序本身就是观感的一部分，
「同样一组参数换个顺序就是另一个效果」，而这是最容易在重构中被无声改掉的东西。

## 4. 三类实现成本（决定了分批）

| 类 | 含义 | 批次 | 架构改动 |
|---|---|---|---|
| **P** 逐像素 | 只看当前像素，可进 `PixelProgram` 的分带零分配路径 | 1 / 2 | 无（只扩 `finish`） |
| **C** 需坐标 | 需要 `x, y` 或归一化坐标 | 3 | **改 `applyLinear` 签名**或加后置 pass |
| **N** 需邻域 | 需要周边像素（模糊核） | 4 | **新增渲染通路**，分带需外扩核半径 |

⚠️ **`PixelProgram` 的「零分配」是它存在的理由**（其 KDoc 明确写了：旧版每像素返回 `Triple`，
33MP 导出约 1.6 亿次分配，与「亚秒级」自相矛盾）。
所以 HSL 实现**必须**：
- 在**构造期**把 `List<Float>` 塌缩成 `FloatArray(8)`（构造期分配不算逐像素分配）；
- 逐像素路径上只用局部 `float` 变量，**不得** `FloatArray(3)` 来回装 RGB/Hue；
- 三通道回写继续走 `finish()` 里的三个局部变量，不引入任何新对象。

## 5. 必须先行修复的前置项：`linear16ToSrgb` 白点硬截断

**这不是新功能，是一个已有缺陷，而它恰好挡在所有高光相关参数前面。**

`ColorMath.linear16ToSrgb` 当前：

```kotlin
fun linear16ToSrgb(v: Float): Float = when {
    v <= 0f      -> 0f
    v >= 65535f  -> 1f          // ← 硬截断，没有任何滚落（rolloff）
    else         -> LINEAR16_TO_SRGB[(v + 0.5f).toInt()]
}
```

`LINEAR16_TO_SRGB` 只有 65536 项（索引 0..65535），所以**线性值一旦 ≥ 65535 就永远等于 1.0**。
后果：

1. 曝光 +1EV 后，任何原本亮度 > 0.5 线性的高光**当场丢失**，`highlights` 滑块拉负也救不回来
   ——它只能压已经存在的值，压不出被截掉的层次；
2. 新增的 `whites` / `highlightRecovery` 会表现得像「坏掉的滑块」（拉不动或只是整体变暗）；
3. 这是审计项 **M1**，早已记录在案。

**修法（批次 1 内联做）**：在**线性域**加软压肩，把 > 白点的部分按比例滚落，而不是钳死。
最小改动版：把查表索引上限从「钳到 65535」改为「对 `v > 白点` 做
`1 − exp(−(v−白点)/肩宽)` 的滚落后再查表」，并给 `highlightRecovery` 一个 0..1 的肩宽系数。
**必须在批次 1 落地**——否则批次 1 的高光类参数无法验收。

### 6.2 UI 分类重排：**现状 5 个一级分类，内容重排**

现状 5 个一级分类（人像/调色/曲线/LUT/预设）。参数翻数倍后，一级必须重排，
否则「调色」一个分类里要装 20+ 个滑块 —— 那正是 `ParamPanel` KDoc 明确批判过的
「仪表盘式界面：把复杂度原样丢给用户排序」。

**目标形态**（含批次 4，**已全部落地**）：

| 一级 | 二级 chip 行 | 内容 | 项数 |
|---|---|---|---|
| 人像 | 画布工具 /（美型、追色为常显分组） | 不变 | — |
| **调色** | 影调 / 白平衡 / 偏好 | 曝光·对比·高光·阴影·白场·黑场 + 高光找回 ‖ 色温·色调 ‖ 自然饱和度·饱和度·去朦胧 | 12 |
| **颜色** | 混色 / 分级 / LUT | 8 通道 × HSL ‖ 4 区 × HSL + 混合 + 平衡 ‖ 内置 LUT | 40 |
| 曲线 | 亮度 / 红 / 绿 / 蓝 | 每通道 3 锚点 | 12 |
| **细节** | 锐化 / 降噪 / 质感 | 强度·半径·细节·蒙版 ‖ 亮度·亮度细节·色度·色度细节 ‖ 清晰度·纹理 | 10 |
| **效果** | 暗角 / 颗粒 | 强度·起点·过渡·圆度 ‖ 强度·尺寸·对比 | 7 |
| 预设 | — | 不变 | — |

**实际落地 = 81 项**（原 10 项 ⇒ 新增 71 项）：调色 12 + 颜色 40 + 曲线 12 + 细节 10 + 效果 7。
其中批次 1 + 2 = 64 项（新增 54）、批次 3 = +7、批次 4 = +10。

- **一级分类 5 → 7（新增「细节」与「效果」）**：新增的两个都排在**曲线之后、预设之前**，
  且「细节」在「效果」**之前**。判据是概念层级 —— 调色改的是「这个像素什么颜色」；
  细节改的是「画面的**结构与质感**」（降噪 / 锐化 / 清晰度）；效果是往这个结构上**再加一层**
  （暗角 / 颗粒）；`预设` 留在最右端当稳定的肌肉记忆锚点。
- **⚠️ 一级上限是 7，不是 6（2026-09-23 批次 4 修正）**：判据是「每项至少 40dp」——
  `labelMedium` 双汉字约 24dp，两侧各留 ≥8dp ⇒ 每项 40dp 起。`GlassSegmentedBar` 等宽分配、
  条内 `padding(Spacing.xs)` 每侧 4dp ⇒ 320dp 屏可用 **312dp**：`312/7 = 44.6dp`（够）、
  `312/8 = 39dp`（不够）。所以**加到第 8 个才必须让工具条横向可滚**。
  上一轮写的「6 个 × 每项约 56dp ⇒ 加到第 7 个就必须可滚」是**估计偏保守 + 算式算错**，
  判据本身没变。改这条之前请照上面这套推导重算，**不要凭「看着挤」下结论**。
- **LUT 从一级降为「颜色」的二级**：它和 HSL、分级一样都是「给画面着色」，
  单独占一个一级分类是概念层级错位（`ParamPanel` 的 KDoc 已经写了这条判据：
  「判据是内容量而不是概念上够不够独立」）。降级**不**增加一级个数。
- **「细节」是最后一个有资格进一级的**：到第 7 个为止，「内容量够撑起一个分类」与
  「工具条放得下」两个条件**同时**成立。下一个候选必须先解决「工具条可滚」才有资格进来。
- **暗角 / 颗粒合成一个一级分类而不是两个**：它们共享的是**实现前提**（都需要坐标），
  不是观感。拆成两个分类会让「效果」这个层级里出现两个只有三四个滑块的入口。
- 二级 chip 行的模式**已有现成实现**（人像分类的「画布工具」就是）；批次 3 新增的只有
  「把 chip 行钉在滚动之外」与「chip 上的色块槽」两件小事。
- 二级分组的顺序**按使用频次**排，与一级分类同一条约定（见 `EditorCategory` 的 KDoc）：
  `调色` 默认落在「影调」而不是「白平衡」，因为曝光/对比度是一天要动几十次的动作，
  而白平衡在暗房流程里虽更靠前、却一天动不了几次 —— 让低频项默认占据面板，
  等于每次调曝光都多点一次。同理 `细节` 默认落在「锐化」（几乎每张都会给一点），
  而不是「降噪」（只在脏图 / 高 ISO 才动）。

### 6.3 一个必须拍板的语义决定：高光滑块的正负号

现有代码：`r -= highlights * lum * 0.5` ⇒ **正值 = 压暗高光**（「拉回」语义）。
Lightroom：**正值 = 提亮高光**。

两者相反。四区影调重构时应当统一到 **Lightroom 约定（正 = 亮）**：
- 好处：与所有主流软件一致，用户迁移无成本；四个滑块方向统一（正=往亮推）后心智负担最低；
- 风险：已有行为翻转。**但现有 10 个预设都没有用到 `shadows` / `highlights`**
  （逐个核过：只用了 `exposureEv` / `contrast` / `saturation` / `temperature` / `lutId`），
  **所以翻转是安全的**；一旦 JSON 存档落地就不再安全。

| 批次 | 单像素新增代价（估） | 预览（2.8MP 代理图） | 导出（33MP） |

| 批次 1 | +~15 flops（4 权重 + vibrance） | 无感 | +10~20% |
| 批次 2 | +~40 flops + 分支（HSL 是大头） | 通常仍跟手 | **+1~3s（需实测）** |

## 7. 分批实施计划

| 批次 | 内容 | 成本类 | 前置 | 风险 | 状态 |
|---|---|---|---|---|---|
| **1** | 四区影调（黑场/阴影/高光/白场）+ 自然饱和度 + 去朦胧近似 + **修 `linear16ToSrgb` 硬截断 + 高光找回** + 高光符号统一 + 耗时日志 | P | 无 | 低（管线不动） | ✅ 已落地 |
| **2** | HSL 混色 8 通道 + 彩色分级（4 区）+ 分通道 RGB 曲线 | P | 无 | 中（HSL 是逐像素成本大头） | ✅ 已落地 |
| **3** | 暗角 + 颗粒 | C | 给 `PixelProgram` 传坐标 | 中（归一化坐标纪律） | ✅ 已落地 |
| **4** | 清晰度 / 纹理 / 锐化 / 降噪 | N | 独立第二遍 pass（**不改分带架构**） | 中（邻域口径：只承诺观感一致） | ✅ 已落地（代码完成，待 CI + 真机） |

**顺序 1 → 2 → 3 → 4，每批独立真机验收**。理由：

- 批次 1 是**唯一一批能顺带修掉一个已知缺陷**的，性价比最高；
- 批次 2 是「调色范围」真正变宽的那一步，且不碰架构；
- 批次 3 首次需要坐标 ⇒ 会改 `PixelProgram` 签名，值得单独一批观察回归面；
- 批次 4 是新渲染通路，混在前三批里做会让「哪里出的问题」无法定位。
  ⚠️ **但它的风险与批次 3 不同类**：批次 3 改的是**签名**（漏一个调用点就编译不过，
  CI 必拦），批次 4 改的是**口径**（邻域算子跨分辨率只能承诺观感一致，编译与单测都拦不住
  口径漂移）。所以它的验收重心在真机目视（§8 第 9~13 条），不在离线闸门。

## 8. 验收方式

**离线闸门（本地无编译器，同既有纪律）**
1. 括号字节配平（`app/src` 全部 `.kt`，`unbalanced = 0`）；
2. 跨文件引用核对（`EditParams` 新字段的定义点 / `copy` 调用点 / UI 读取点全量比对）；
3. 逐像素路径**零分配自检**：新增代码里不得出现 `FloatArray(` / `Triple` / 装箱（比对 `finish()` 的写法规约）。

**真机（一加 15）**
1. 影调四区**互不串扰**：拖白场不应改变阴影区亮度（可用灰阶图目视）；
2. 高光找回：曝光 +1.5EV 后拉 `highlightRecovery`，云层细节应回来（当前是死的）；
3. HSL 单通道：只推「橙色→明度」，肤色应变亮而背景不变；
4. 分级：阴影偏青 + 高光偏橙，中性灰不应偏色；
5. 暗角：拖 `vignetteAmount` 时**画面中心必须纹丝不动**（动了就是 `buildVignetteLut` 的
   `mid − half` 没下夹 0）；四角**左右上下对称**（归一化到四角 = 1）；
   `起点` / `过渡` / `圆度` 三个旋钮应分别给出「范围 / 软硬 / 方圆」的直观变化；
6. 颗粒：**拖动任何滑块时噪点不得抖动**（抖了就是用了 `Random` 或逐像素哈希）；
   三通道同加 ⇒ 不应出现彩色噪点；`尺寸` 拉到两端应表现为「细密 ↔ 粗大」而不是「没有 ↔ 更粗」；
7. **预览与导出目视一致**（第 5 / 6 条的暗角范围与颗粒粗细都不随分辨率变）：
   这是本批唯一的新增不变量，也是最容易只在一个方向上验证对的一条（导出后按同尺寸并排看）；
8. 性能：`DebugLog` 的渲染耗时，预览应 ≤ 现基线 +30%；
   暗角 / 颗粒**关闭**时（默认）应与批次 2 的读数基本一致 —— 只多算一对坐标。

**批次 4 追加（细节：锐化 / 降噪 / 质感）**

9. **锐化必须晚于磨皮**（本批最重要的顺序不变量）：人像分类里把磨皮强度拉到 0.5+，
   再回「细节」拉锐化 —— 边缘应变锐。**反例**：若锐化落在磨皮**之前**，拉锐化几乎看不出变化
   （量程被吃掉一半）。这是三条渲染入口都必须同序的理由，也是本批唯一「错了画面仍然正常、
   只是效果变弱」的坑。
10. **只压色度不该糊细节**：高 ISO 图上 `色度` 拉满、`亮度` 保持 0 ⇒ 彩斑应消失而发丝 /
    织物纹理仍在。再把 `亮度` 拉满 ⇒ 细节明显变肉 —— 这是**正确的取舍**，不是 bug。
11. **清晰度 / 纹理不应产生白边**：`清晰度` 拉满时建筑边缘不应出现「描边」。
    出现白边说明反边缘门（纹理那一路）失效，或偏移被误加到了高频带。
12. **预览与导出观感一致（本批只能验到这一层）**：同一张图的锐化粒度、降噪块大小在预览
    与导出上应一致。**不要逐位比对** —— 邻域算子跨分辨率不保证逐位（见 §12 第 2 条）。
13. **性能**：导出必打的 `DebugLog` 里有独立的 `detail pass` 一行（`w/h/ms`）；
    33MP 全开应在**数百毫秒**量级；而 10 项**全默认**时**不该出现这条日志**（`isNeutral` 短路）
    —— 出现了就说明短路判据与 `DetailPass.isNeutral` 不一致（那是最难查的性能问题）。

### 11.2 实施中新增/收紧的决定（规格里没写、但代码里做死了）

1. **暗角表的索引是 `d²` 而不是 `d`**：省掉逐像素 `sqrt`（33MP 上是几十毫秒）。代价是近中心处的
   径向分辨率偏粗 —— 而那恰好是「权重必须恰好为 0」的区域，代价落在空处。
   表长取 **1024**（不是 256）：256 项在过渡区会留 1% 的权重台阶，乘 255 就是 2~3 级灰度，
   渐变天空会出色带。
2. **`mid − half` 下夹 0**：不夹的话 `midpoint = 0` + `feather = 1` 会让权重在**中心**就大于 0
   —— 表现为「调暗角，画面中心跟着暗」。这是本批最容易写漏、真机上又最像「曝光坏了」的一处，
   `EffectMathTest.vignetteLutIsExactlyOneAtTheCentre` 就是钉它的。
3. **颗粒的「尺寸」不烘进瓦片，而是体现在采样密度里**：瓦片只有一张（进程内建一次，
   `grainAmount = 0` 的用户一次都不付），一张瓦片覆盖整段量程。若按尺寸各烘一张，
   要么启动变慢，要么得在渲染线程里建表。
4. **`grainRoughness` 的幂整形在构造期塌缩成 256 项表**：逐像素一次 `powf` 在 33MP 上是
   几十毫秒。整形必须**带符号**做（`(−0.5f).pow(0.4f)` 是 NaN，而噪声一半是负的）。
5. **颗粒排在暗角之后**：暗角是镜头里的光学衰减、颗粒长在乳剂上，两者独立 ⇒
   被压暗的角落会「显得」颗粒更明显，这正是胶片扫描件的观感。反过来做会让四角一起变干净。
6. **`(u, v)` 刻意不给默认值**：给个 `0.5f` 就能让「某个调用点忘了传坐标」退化成
   「暗角 / 颗粒静默失效」，而那正是这一批最需要防的错误。**编译不过比跑错好** ——
   代价是 4 个测试文件的调用点必须同批改完（已全部改完）。
7. **`runBand` 改成按行分片**：旧签名只递扁平下标，调用方要坐标就得 `i % w` / `i / w`。
   按行分片后 `y` 在行内是常量、`x` 就是内层计数器 —— 热循环里一个除法都没有。
   代价是负载均衡从「按像素」变成「按行」（32 行 / 8 核 = 每片 4 行），可接受。

### 12.2 实施中新增/收紧的决定（规格里没写、但代码里做死了）

1. **邻域算子做成「目标位图上的独立第二遍 pass」，不插进逐像素管线。** 三条理由（完整版在
   `DetailPass` 的类 KDoc）：① 不碰批次 3 刚改的 `(u, v)` 签名 ⇒ 回归面不叠加；
   ② RAW / JPEG 两条输入已在上游汇合于 `Bitmap` ⇒ 「预览所见 = 导出所得」是**结构性**成立；
   ③ 阈值可以按 0..255 的**绝对级数**给（线性域的亮度分布随曝光漂移，同一阈值在不同照片上含义不同）。
   与既有 `retouch/NeutralGray` 同口径（它同样在 8-bit 上做）。

2. **⚠️ 口径降级：本批**不能**承诺「预览与导出逐位相同」。** 批次 3 是 `(u, v)` 的纯函数，
   逐位一致是**可以**承诺的；邻域算子的输出依赖核半径与邻域内容，跨分辨率时半径按长边的固定比例
   等比缩放 ⇒ 得到的是**同一个观感**而不是同一个数字。唯一承诺：**核半径随长边等比 ⇒ 观感一致**。
   `DetailPassTest` 只断言半径「只依赖长边」与「随长边单调」，**刻意不断言**跨分辨率逐位相等 ——
   那对一个邻域算子根本不该成立，写出来就是假护栏。

3. **管线顺序：`逐像素调色 → 人像精修 → 细节 → 导出`（三条入口必须同序）。** 四个算子里锐化
   对顺序最敏感：锐化必须晚于磨皮，否则磨皮（本身就是一次表面模糊）会把刚锐出来的边缘糊掉 ——
   真机表现为「锐化滑块的量程只有一半」。代价是降噪也落在调色之后（理性位置本应更早），
   这是**刻意接受的取舍**：锐化被糊肉眼可见，降噪晚一步只是效率问题。

4. **频带切法：一趟复合模糊切出高中低三段。** `b1 = blur(rFine)`、`b2 = blur(b1, rCoarse)`
   （复合 ⇒ 三角核，总共只要两趟模糊）。`hi = Yd − Y1`（锐化）、`mid = Y1 − Y2`
   （纹理 + 锐化的 detail 项）、`low = Yd − Y2`（清晰度）。`Yd` 是**降噪之后**的亮度 ——
   降噪先做，否则锐化会把刚压掉的噪声重新提回来。

5. **降噪必须分通道，其余三项必须「三通道同加同一偏移」。** 后者保持不变量：三个亮度权重和为 1
   ⇒ 亮度恰变 `off`，而 `R−Y` / `B−Y` 不变 ⇒ 色相饱和度不动（与影调四区 / 暗角 / 颗粒同一条约定，
   也是「清晰度不会让画面变脏」的原因）。降噪相反：亮度降噪 = 三通道等比缩放（保色相）；
   色度降噪 = 只拉 `(R−Y, B−Y)` 朝 `b2` 的对应量，再由 `Y = R_Y·r + G_Y·g + B_Y·b` 反解 `g`
   （三权重和为 1 ⇒ 亮度恰仍为 `yd`）。

6. **`guard` 的 `t ≤ 0 ⇒ 0` 与「蒙版 0 ⇒ 全图锐化」是**相反**语义，必须特判。** `guard` 的 0
   承载「细节 = 100% ⇒ 不做降噪」；而蒙版 0 要的是「无限制」（返回 1）。把 `tMask` 直接交给
   `guard` 会让**默认值下锐化完全失效**（滑块没反应）。

7. **分带照 `NeutralGray` 的样板，但窗口 `[win]` 只读**（结果另写 `out`）⇒「读到已写过的值」
   在结构上不可能。顶部 halo 用上一带**留存的原始行**（核心行写回平面后，平面里的顶部 halo
   已是处理过的值）。不变式 `carry.size == rMax * w` 恒成立（`headRows ≤ rMax`）
   ⇒ 越界是响亮的断言，不是静默降质。

8. **`boxPass` 与 `NeutralGray.boxPass` 同构但刻意不复用**：后者是 retouch 包内 private；
   两者唯一的共同点只是「都用盒式模糊」，半径来源、作用域、精度口径全不同。
